Lo que más preguntan en la defensa interna

Conceptos clave, explicados con tu propio código

Estas son las preguntas de teoría que ya te hicieron en la defensa interna (CORS, WebSockets, localStorage...). Cada respuesta está conectada directamente con un archivo real de PetCore, para que no suene memorizada.

CORS (Cross-Origin Resource Sharing) es el mecanismo del navegador que decide si un sitio web (origen A) puede hacer peticiones a una API que vive en otro dominio (origen B). Por defecto el navegador bloquea esas peticiones "cruzadas" por seguridad, a menos que el servidor diga explícitamente que las permite.

En PetCore, el navegador carga el frontend desde vercel.app y ese frontend llama a la API en herokuapp.com — son dominios distintos, así que sin CORS el navegador bloquearía todas las peticiones.

La configuración vive en security/cors/CorsConfig.java: define una lista blanca de orígenes permitidos (Vercel, Heroku, localhost de desarrollo, capacitor://localhost para la app móvil), los métodos HTTP permitidos (GET, POST, PUT, PATCH, DELETE, OPTIONS) y allowCredentials=true, que es obligatorio porque la sesión viaja en una cookie.

Frase para la defensa: "CORS no es una medida de seguridad contra atacantes — es una política del navegador para que un sitio no use, sin permiso, las credenciales de otro. La seguridad real de quién puede hacer qué la decide Spring Security en el backend, no CORS."

HTTP normal es "pregunta-respuesta": el cliente pide, el servidor responde, y la conexión se cierra. Un WebSocket abre un canal bidireccional y persistente entre navegador y servidor — ambos pueden enviar mensajes en cualquier momento sin que el cliente tenga que estar preguntando ("polling") cada cierto tiempo.

PetCore implementa WebSocket puro (sin STOMP, sin un broker de mensajes) en config/websocket/WebSocketConfig.java + EventoWebSocketHandler.java, con un único endpoint /ws. El servidor hace broadcast: cuando pasa algo relevante (nueva cita, nueva notificación), envía un evento JSON {evento, datos} a todas las sesiones conectadas, y el frontend (websocket_service.js) decide a cuáles le interesa reaccionar.

Se usa para: la campanita de notificaciones en tiempo real, el indicador de conectado/desconectado en el navbar, y actualizar citas/asistencias sin que el usuario tenga que recargar la página.

localStorage es un almacenamiento del navegador, por dominio, que persiste aunque se cierre la pestaña — y es accesible desde cualquier JavaScript que corra en esa página, incluido código malicioso inyectado por un ataque XSS.

Por eso PetCore no guarda el token de sesión en localStorage. Lo guarda el servidor en una cookie httpOnly (authToken), que JavaScript no puede leer ni robar aunque exista una vulnerabilidad XSS — solo viaja automáticamente con cada petición al dominio de la API.

Lo único que sí usa localStorage en PetCore son preferencias de interfaz sin información sensible: tema claro/oscuro, animaciones, formato de hora, opacidad de fondo. Si lo robaran, lo peor que pasa es que alguien sepa si prefieres el modo oscuro.

Esta es una de las mejores respuestas que puedes dar en la defensa: demuestra que el equipo entendió el riesgo de XSS y migró a un patrón más seguro a propósito.

Un JWT (JSON Web Token) es un texto firmado digitalmente con 3 partes (header.payload.signature) que contiene información del usuario (en PetCore: id, correo, rol, tipo de cuenta) y una firma que garantiza que nadie lo alteró sin conocer la clave secreta del servidor.

El patrón típico en tutoriales es mandar el JWT en el header Authorization: Bearer ... y guardarlo en localStorage. PetCore usa un patrón más seguro: el servidor genera el JWT y lo entrega dentro de una cookie httpOnly (security/jwt/JWTUtils.java, firmado con HMAC-SHA256). Así se combina lo mejor de ambos mundos: el token sigue siendo stateless (el servidor no guarda una tabla de sesiones), pero JavaScript no puede acceder a él.

Además, implementa sesión deslizante: cada request válido renueva la cookie (15 minutos de vida útil), así que un usuario activo nunca se desconecta solo, pero uno inactivo sí expira.

CSRF (Cross-Site Request Forgery) es un ataque donde un sitio malicioso hace que el navegador de la víctima envíe, sin que se dé cuenta, una petición a otra app donde sí tiene sesión activa (aprovechando que las cookies se mandan automáticamente).

PetCore mitiga esto con varias capas: la cookie authToken se configura con SameSite (restringe cuándo el navegador la envía en peticiones de origen cruzado) y Secure (solo viaja por HTTPS). Además, CORS ya limita qué orígenes pueden siquiera recibir respuesta de la API, y al ser una API JSON pura (no formularios tradicionales que un atacante pueda replicar fácilmente), la superficie de ataque de CSRF clásico se reduce bastante. Por eso el equipo decidió deshabilitar la protección CSRF integrada de Spring Security (pensada para apps con sesiones de formulario) y apoyarse en SameSite + CORS + JWT.

Cuando navegas "Atrás", muchos navegadores no vuelven a cargar la página desde cero: la restauran desde una caché especial llamada bfcache (back-forward cache), con el DOM tal como estaba. Si no se maneja, un usuario podría cerrar sesión, pulsar "Atrás" y ver el dashboard anterior todavía dibujado en pantalla.

PetCore soluciona esto escuchando el evento pageshow en cada página protegida:

window.addEventListener("pageshow", (e) => {
  if (e.persisted) location.reload();
});

La propiedad event.persisted es true solo cuando la página viene del bfcache. Al forzar un reload(), se vuelve a ejecutar el guard de sesión (verificarSesionSync()), que detecta que ya no hay cookie válida y redirige al login.

PetCore sigue un patrón de seguridad llamado "deny by default" (denegar por defecto): en SecurityConfig.java, cada endpoint tiene que tener una regla explícita de quién puede usarlo, y la última línea de toda la configuración es:

auth.anyRequest().denyAll();

Esto significa que si alguien crea un endpoint nuevo y se olvida de agregar su regla de autorización, ese endpoint queda bloqueado automáticamente en vez de quedar abierto por accidente. Es la opción contraria (y más segura) a tener una lista negra de rutas prohibidas, donde olvidarse de una ruta significa dejarla expuesta.

Es para los propietarios de mascotas en la app móvil (no para el personal). El flujo: el plugin SocialLogin de Capacitor abre el selector de cuentas de Google en el dispositivo, Google devuelve un ID Token firmado por Google, y ese token se manda al backend.

En el servidor, auth/google/GoogleTokenVerifier.java usa la librería oficial google-api-client para verificar la firma del token directamente con los servidores de Google (nunca se confía ciegamente en lo que manda el cliente). Si es válido, PetCore crea o vincula el PropietariosEntity usando el pro_google_id, y emite su propia cookie authTokenPropietario igual que en un login normal.

Parcialmente. sw.js no implementa cacheo de assets estáticos (no es "offline-first" como una PWA completa) — su única función es recibir y mostrar notificaciones push del navegador: escucha el evento push, parsea el payload JSON que manda el backend (firmado con claves VAPID vía la librería web-push) y llama a showNotification.

Esto es distinto del push nativo de la app móvil, que usa Firebase Cloud Messaging (dependencia firebase-admin en el backend) — son dos canales de entrega separados para dos plataformas distintas, pero conceptualmente cumplen el mismo propósito: avisar al usuario aunque no tenga la pestaña/app abierta.

En ambos, con propósitos distintos. El frontend valida (HTML5 required/type/pattern + JavaScript) para dar feedback inmediato al usuario sin esperar un viaje al servidor — pero esa validación se puede saltar fácilmente (herramientas de desarrollador, Postman, un script).

Por eso la validación que realmente garantiza la integridad de los datos ocurre en el backend, con anotaciones de Bean Validation en los DTO (@NotBlank, @Email, @Pattern, @Past) y el GlobalExceptionHandler que convierte cualquier fallo de validación en una respuesta 400 clara. La regla de oro: nunca confiar en que el dato ya viene validado solo porque pasó por el frontend.

PetCore usa Capacitor, un framework que toma una app web (el mismo HTML/CSS/JS del frontend, sin frameworks) y la empaqueta dentro de un WebView nativo, dándole acceso a APIs del dispositivo (cámara, almacenamiento, notificaciones push nativas) mediante plugins.

Ventaja principal: un solo código fuente para web y móvil — cualquier corrección o nueva funcionalidad en las páginas HTML/CSS/JS se refleja en ambas plataformas sin duplicar trabajo. Lo que sí es 100% nativo son los plugins: notificaciones push, acceso al sistema de archivos, compartir, status bar — esos sí usan APIs reales de Android/iOS.

REST (Representational State Transfer) es un estilo de arquitectura para APIs que organiza todo alrededor de recursos (sustantivos: /api/mascotas, /api/citas) en vez de acciones (verbos), y usa los métodos HTTP para expresar la operación: GET para leer, POST para crear, PUT/PATCH para actualizar, DELETE para eliminar.

PetCore sigue este estilo en todos sus 51 módulos: cada controller expone rutas como /api/mascotas/{id} y el verbo HTTP determina qué hace, en vez de tener rutas como /api/obtenerMascota o /api/borrarMascota. Además es stateless (cada petición trae toda la información necesaria, el servidor no recuerda peticiones anteriores), otro principio clave de REST.

Un DTO (Data Transfer Object) es un objeto simple que define exactamente qué datos viajan entre el frontend y la API — distinto de la entidad JPA, que representa la tabla completa de la base de datos con todas sus relaciones.

Exponer la entidad directamente sería peligroso y poco práctico: podría filtrar campos sensibles (como el hash de la contraseña, si no se marca con cuidado), arrastrar relaciones completas innecesarias (ej. traer todos los expedientes de una mascota solo por pedir su nombre) y acoplar la estructura de la base de datos directamente a lo que ve el cliente. Por eso cada módulo de PetCore tiene su propio dto/ separado de su entity/, con Bean Validation aplicada solo en el DTO.

Un ORM (Object-Relational Mapping) como Hibernate traduce automáticamente entre objetos Java y filas de una tabla SQL, para no tener que escribir SQL a mano para cada operación. El problema N+1 es un error de rendimiento clásico: si cargas una lista de 50 mascotas y luego, por cada una, Hibernate hace una consulta aparte para traer su propietario, terminas con 1 consulta inicial + 50 consultas adicionales (51 en total) en vez de una sola consulta optimizada.

PetCore lo mitiga configurando hibernate.default_batch_fetch_size=50 en application.properties, que agrupa esas consultas adicionales en lotes en vez de hacerlas una por una — el comentario del propio archivo menciona explícitamente el caso de CitasEntity.serviciosCita como motivo de este ajuste.

Maven es el gestor de dependencias y herramienta de construcción (build) para proyectos Java. El pom.xml ("Project Object Model") declara qué librerías externas necesita el proyecto (Spring Boot, JWT, Oracle driver, etc.) con su versión exacta, y Maven se encarga de descargarlas, resolver conflictos entre ellas, compilar el código y empaquetarlo en el .jar ejecutable que termina corriendo en Heroku.

Sin Maven, el equipo tendría que descargar manualmente cada librería y sus dependencias transitivas — con ~16 dependencias directas en PetCore, eso sería inmanejable a mano.

Un servidor stateless no guarda información de una petición para la siguiente — cada request debe traer todo lo que el servidor necesita saber (en PetCore, el JWT dentro de la cookie). Lo opuesto es stateful, donde el servidor mantiene una tabla de sesiones activas en memoria o base de datos.

Ser stateless es clave para PetCore porque Heroku puede reiniciar el dyno en cualquier momento (y perder toda la memoria) o, en teoría, correr múltiples instancias — un diseño stateful perdería las sesiones activas en cualquiera de esos casos, mientras que el JWT sigue siendo válido sin importar qué instancia del servidor lo reciba, porque la validación depende solo de la firma criptográfica, no de un estado guardado.

Una operación es idempotente si hacerla una vez o cien veces produce el mismo resultado final. GET (leer) y DELETE (eliminar) deben ser idempotentes: pedir el mismo recurso dos veces no debería cambiar nada, y eliminar el mismo registro dos veces debería dejar el sistema en el mismo estado que eliminarlo una sola vez (la segunda vez simplemente ya no existe). PUT también es idempotente (reemplaza el recurso completo con los mismos datos), pero POST (crear) no lo es — llamarlo dos veces crea dos registros distintos.

Por qué importa: el interceptor de reintentos de PetCore (fetch_con_credenciales.js) solo reintenta automáticamente peticiones GET/HEAD ante errores de red — nunca reintenta un POST automáticamente, precisamente para no arriesgarse a crear un registro duplicado si la primera petición sí llegó a procesarse pero la respuesta se perdió en el camino.

HTTPS es HTTP cifrado mediante TLS (Transport Layer Security): toda la comunicación entre el navegador y el servidor viaja encriptada, de modo que alguien espiando la red (por ejemplo en un WiFi público) no puede leer ni modificar los datos en tránsito.

Es especialmente importante para la cookie authToken: tiene el atributo Secure, que le dice al navegador "nunca envíes esta cookie por una conexión HTTP sin cifrar". Vercel y Heroku sirven el sitio y la API por HTTPS por defecto, así que esa condición siempre se cumple en producción — sin TLS, aunque la cookie sea httpOnly, viajaría en texto plano y cualquiera en la misma red podría leerla.

Un índice es una estructura auxiliar que la base de datos mantiene para encontrar filas rápidamente sin tener que revisar la tabla completa fila por fila — funciona de forma parecida al índice de un libro: en vez de leer todas las páginas buscando un tema, el índice te dice directamente dónde está.

En PetCore, las llaves primarias y únicas (PK_, UQ_) generan índices automáticamente en Oracle, y las convenciones del proyecto reservan el prefijo IX_ para índices adicionales creados a propósito en columnas que se consultan muy seguido pero no son llave (por ejemplo, buscar citas por fecha). Sin índices, una tabla con miles de expedientes clínicos se volvería progresivamente más lenta de consultar a medida que crece.

Una transacción agrupa varias operaciones de base de datos para que se ejecuten como una sola unidad: o se completan todas, o no se aplica ninguna. Por ejemplo, registrar una venta en farmacia implica insertar en TBL_VENTAS, insertar en TBL_DETALLE_VENTA y descontar stock en TBL_MOVIMIENTO_INVENTARIO — si el descuento de stock fallara a mitad de camino, la transacción completa se revierte (rollback) para no dejar una venta registrada sin su movimiento de inventario correspondiente.

ACID son las cuatro garantías que debe cumplir: Atomicidad (todo o nada), Consistencia (nunca deja la base de datos en un estado inválido), Isolación (transacciones simultáneas no se interfieren entre sí) y Durabilidad (una vez confirmada, sobrevive incluso a un apagón). Spring maneja esto con la anotación @Transactional en los services.

Ambos son algoritmos diseñados específicamente para hashear contraseñas (lentos a propósito, con "salt" integrado para que dos contraseñas iguales no den el mismo hash). La diferencia principal es que Argon2 es más reciente (ganador de la Password Hashing Competition 2015) y está diseñado para ser costoso también en memoria, no solo en tiempo de CPU — eso lo hace más resistente a ataques que usan hardware especializado (GPUs, ASICs) para probar millones de contraseñas en paralelo, algo a lo que bcrypt es más vulnerable al depender solo de costo de CPU.

VAPID (Voluntary Application Server Identification) es un estándar que permite que un servidor se identifique ante los servicios push de los navegadores (Chrome, Firefox) sin depender de una cuenta propietaria de cada navegador. PetCore genera un par de claves VAPID (pública/privada): la pública se expone en un endpoint abierto (/api/push/vapid-public-key) para que el navegador del usuario se suscriba, y la privada la usa el backend (librería web-push, con BouncyCastle para el cifrado ECDH) para firmar cada notificación antes de enviarla — así el navegador puede confirmar que la notificación realmente viene del servidor de PetCore y no de un tercero.

Los tres resuelven "una app para Android y iOS con un solo código", pero de formas muy distintas: Flutter y React Native compilan a componentes de interfaz nativos reales (o casi), requieren aprender su propio framework (Dart o React) y reescribir toda la interfaz desde cero. Capacitor, en cambio, no reemplaza la interfaz — toma la app web que ya existe (HTML/CSS/JS, tal como la pide esta rúbrica) y la ejecuta dentro de un WebView nativo, exponiendo plugins para acceder a funciones del dispositivo.

Para PetCore esto significó poder reutilizar el 100% del frontend web para la app móvil sin aprender ni mantener un stack completamente aparte — el costo es que el rendimiento de la interfaz depende del motor WebView del sistema operativo, en vez de ser un componente nativo puro.
