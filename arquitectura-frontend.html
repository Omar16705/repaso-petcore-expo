Frontend · HTML / CSS / JS puro + App móvil Capacitor

Arquitectura del Frontend y la App Móvil

HTML, CSS, Bootstrap 5.3.8 y JavaScript sin frameworks (nada de React/Vue/Angular — tal como exige la rúbrica), desplegado en Vercel. La app móvil usa Capacitor para empaquetar ese mismo frontend dentro de un WebView nativo Android/iOS.

Organización

Patrón Controller / Service, páginas por rol

El frontend replica en JavaScript puro una idea parecida al MVC: cada página tiene un controller que maneja el DOM/eventos, y delega todo fetch a la API a un service dedicado a esa entidad.

📁 js/controllers/

~69 archivos. Un controller por página (ej. citas_admin_controller.js). Maneja eventos de botones, formularios, tablas y pinta los datos en el DOM.

📁 js/services/

~136 archivos. Un service por entidad (ej. citas_service.js). Son los únicos archivos que hacen fetch a la API — los controllers nunca llaman a fetch directamente.

📁 js/utils/

Helpers compartidos: alertas (SweetAlert2), formato de fechas, selects/datepickers personalizados, lector de código de barras, generación de PDF.

pages/ organizado por rol (espejo del RBAC del backend)

Administrador

20 páginas: personal, inventario (+categorías/marcas/proveedores), compras, citas, servicios, turnos, reportes, configuración...

Veterinario

16 páginas: expedientes clínicos, citas, cuidados, alergias, hospitalización (ingresos), posología, reportes...

Recepcionista

9 páginas: citas, sala de espera, registro de mascotas/propietarios, catálogos (especie/raza/pelaje)...

Farmacéutico

7 páginas: punto de venta (POS), stock, posología, registro de ventas...

Más pages/Cuentas/ (login, recuperar contraseña) y pages/Primer_Inicio/ (asistente para configurar el sistema y crear el primer administrador cuando la BD está vacía).

Criterio 7 de la rúbrica

Autenticación: sesión por cookie, no por localStorage

Dato importante para la defensa: el proyecto migró de JWT-en-localStorage a cookie httpOnly. El propio código lo documenta: el comentario en login_controller.js dice textualmente "ya no se guarda nada en localStorage/sessionStorage aquí".

1. Login

login_controller.js → AuthModule.iniciarSesion() llama a loginEmpleado() de login_service.js, que hace POST /api/auth/login/empleado.

2. El backend responde con una cookie httpOnly

La cookie authToken la pone el servidor en la respuesta. JavaScript del navegador nunca puede leerla ni manipularla (eso es justamente lo que significa httpOnly) — solo viaja automáticamente en cada request.

3. Cada fetch incluye credentials: "include"

fetch_con_credenciales.js parchea window.fetch globalmente para que siempre mande las cookies, sin que cada service tenga que acordarse.

4. Verificación de sesión

sesion_service.js → verificarSesionSync() hace un XHR síncrono contra GET /api/auth/me/empleado para bloquear la carga de la página hasta saber si hay sesión válida — algo que un fetch asíncrono no permite hacer antes de que el HTML se pinte.

5. Logout

logout() hace POST /api/auth/logout (el servidor invalida/borra la cookie); el frontend también limpia sessionStorage y el Cache Storage del navegador.

¿Entonces qué SÍ hay en localStorage? Solo preferencias de interfaz sin información sensible: tema claro/oscuro, animaciones activadas, opacidad de fondo, formato de hora 12h/24h, si ya se felicitó el cumpleaños del usuario este año. Cero tokens, cero contraseñas.

Criterio 8 de la rúbrica

Protección de rutas, roles y el botón "atrás"

Guard de página por rol

estructura_base_controller.js → función iniciar(config), llamada al cargar cada página con la lista de roles permitidos:

const sesion = SesionService.verificarSesionSync();

if (!sesion) {
  location.replace('../Cuentas/login.html');
}
if (!config.rolesPermitidos.includes(sesion.rol)) {
  location.replace('../acceso_denegado.html');
}

El rol nunca se decodifica de un JWT en el navegador — siempre se obtiene fresco desde /api/auth/me/empleado, así el backend sigue siendo la única fuente de verdad.

Bloqueo del botón "Atrás" (bfcache)

Tanto el guard de páginas internas como el del asistente de primer uso escuchan el evento pageshow:

window.addEventListener("pageshow", (e) => {
  if (e.persisted) location.reload();
});

Cuando el navegador restaura una página desde su caché de retroceso (bfcache) tras pulsar "Atrás", esto fuerza una recarga real — que vuelve a ejecutar la verificación de sesión y expulsa al usuario si ya cerró sesión.

Interceptor global de fetch

js/controllers/fetch_con_credenciales.js reemplaza window.fetch una sola vez al cargar el sitio, y agrega automáticamente:

  • credentials: "include" en cada llamada (para que la cookie viaje siempre)
  • Reintentos con backoff (1.5s, 3s, 5s, 8s) en errores 502/503/504 — pensado para el "cold start" de Heroku en el plan gratuito
  • Desenvoltura automática del ApiResponse {success, message, data} para que los services solo lean .data
  • Logout automático si cualquier llamada (fuera de /api/auth/) responde 401/403 — la sesión expiró

También existe bloqueo_menu_desarrollador.js, que bloquea F12, clic derecho y atajos de DevTools. Importante aclarar si preguntan: esto es solo disuasión visual, no seguridad real — la seguridad verdadera está en el backend (Spring Security + validación de cada endpoint).

Comunicación con la API

fetch nativo, validaciones y Service Worker

Patrón de llamadas

  • fetch nativo en todos los services (sin axios ni librerías externas)
  • Base URL de Heroku escrita en cada *_service.js
  • Errores capturados con try/catch y mostrados con SweetAlert2 (nunca alert() nativo)

Validaciones en el cliente

  • HTML5 nativo: required, type="email", type="date", maxlength, accept="image/*"
  • Validación manual en JS: longitud de contraseña, confirmación, verificación de duplicados (correo/DUI/usuario) antes de guardar
  • Componentes personalizados que reemplazan los nativos: selects buscables y date-picker propio

Service Worker (sw.js)

Vive en la raíz del sitio (el scope de un Service Worker es, como máximo, la carpeta donde está el archivo). En PetCore no cachea assets estáticos — su único trabajo es soportar Web Push: recibe el evento push, muestra la notificación con el logo de PetCore, y abre/enfoca la pestaña correcta en notificationclick.

Tiempo real

WebSocket en el Frontend

js/services/websocket_service.js — conexión nativa (new WebSocket(...)), sin SockJS ni Stomp.js, hacia wss://petcore-8afada45fabc.herokuapp.com/ws.

Robustez de la conexión

  • Heartbeat manual: ping cada 25s, timeout de pong a los 10s
  • Reconexión automática con backoff exponencial + jitter (1s → 30s)
  • Evento sintético WS_RECONECTADO para que cada página revalide sus datos tras un corte

Para qué se usa

  • Campanita de notificaciones en tiempo real en la sidebar
  • Indicador visual de "conectado/desconectado" en el navbar
  • Actualización en vivo de citas, asistencias y configuración institucional sin recargar

Criterios 3, 5 y 9 de la rúbrica

La app móvil: Capacitor, no una app nativa desde cero

Carpeta PetCore-APP-Oficial/. Capacitor toma el mismo frontend web (HTML/CSS/JS, sin frameworks) y lo empaqueta dentro de un WebView nativo para Android e iOS — confirmado: public/ contiene una copia exacta de css/, js/, pages/ y sw.js del repositorio Frontend.

capacitor.config.json

  • appId: com.petcore.app.oficial
  • webDir: dist (carpeta que genera Vite al compilar)
  • Plugin CapacitorCookies habilitado — imprescindible para que la cookie httpOnly de sesión funcione también dentro del WebView nativo
  • Plugin CapacitorHttp habilitado — las peticiones pasan por el puente nativo en vez del WebView directo
  • SocialLogin (Google habilitado) para el login con Google desde la app

Dependencias (package.json)

  • Proyecto Vite (npm run dev / build / preview)
  • @capacitor/core, @capacitor/android, @capacitor/ios, @capacitor/cli
  • Plugins nativos: @capacitor/push-notifications, @capacitor/filesystem, @capacitor/share, @capacitor/status-bar, @capacitor/app

Criterios 2 y 3 de la rúbrica

Organización del CSS y diseño responsive

Variables CSS + tema claro/oscuro

css/style_global_compartido.css define variables bajo :root[data-theme="dark"]. El tema se alterna cambiando un atributo en <html>, no una clase, y cada página carga dinámicamente su style_X.css o style_X_oscuro.css correspondiente.

Responsive real

  • Media queries explícitas (ej. @media (max-width: 767.98px))
  • @media (prefers-reduced-motion: reduce) por accesibilidad
  • Detección de dispositivo móvil combinando navigator.userAgent + window.innerWidth para decidir sidebar fija vs. menú hamburguesa

Librerías visuales: Bootstrap 5.3.8 (grid, utilidades flex, offcanvas) vía CDN, Animate.css para transiciones y SweetAlert2 para todas las alertas/confirmaciones del sistema.
