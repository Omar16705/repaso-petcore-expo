Backend · Java + Spring Boot

Arquitectura de la API de PetCore

Monolito modular en Java 17 con Spring Boot 4.1, JPA/Hibernate sobre Oracle, desplegado en Heroku. Paquete raíz PTC_PETCORE.API.

Origen del proyecto

¿Cómo se creó en Spring Initializr?

El pom.xml hereda de spring-boot-starter-parent (v4.1.0), lo que confirma que el proyecto nació desde start.spring.io (Spring Initializr) con Maven como gestor de dependencias y Java 17. Luego el equipo fue agregando dependencias por fases, como lo documentan sus propios comentarios en el pom ("1. OBLIGATORIA", "3. HABITUALES: agregar solo si estás creando el proyecto desde cero").

Datos para decir en la defensa

  • Group: PTC_PETCORE · Artifact: API · Packaging: Jar
  • Java: 17 (fijado también en system.properties para que Heroku use el JDK correcto)
  • Build tool: Maven (pom.xml, mvnw / mvnw.cmd como wrapper)
  • Incluye ServletInitializer.java (extiende SpringBootServletInitializer): permite empacar también como WAR, aunque se despliega como Jar ejecutable en Heroku.

Pregunta típica: "¿Por qué JWT en vez de sesiones de servidor?" → Porque la API es stateless (no guarda sesiones en memoria/BD), lo cual escala mejor en Heroku, donde el dyno puede reiniciarse o haber varias instancias. Ver detalle en Conceptos clave.

Arquitectura

Organización modular por feature (no por capa)

En vez de tener una carpeta controllers/ gigante con todo mezclado, PetCore usa 51 módulos verticales (uno por entidad/tabla, más módulos transversales como auth y push) bajo modules/, y cada módulo repite siempre la misma estructura interna de 6 carpetas:

📁 controller/

Clases @RestController. Reciben el HTTP request, llaman al service y devuelven ResponseEntity<ApiResponse<T>>.

📁 service/

Lógica de negocio: reglas, cálculos, orquestación entre repositorios. Nunca usa try/catch — lanza excepciones propias del módulo.

📁 repository/

Interfaces JpaRepository<Entidad, Long>. Spring Data genera las consultas SQL automáticamente.

📁 entity/

Clases @Entity mapeadas a las tablas TBL_* de Oracle, con Lombok y relaciones JPA.

📁 dto/

Objetos de transferencia con las anotaciones de Bean Validation (@NotBlank, @Pattern…) que viajan entre Frontend y API.

📁 exceptions/

5 excepciones propias por módulo (NotFound, Duplicate, Validation, BusinessRule, DataIntegrity) que heredan de clases globales.

El módulo auth/ es especial: no sigue el patrón CRUD. Contiene AuthController, ContraseniaController, RecuperacionController, el verificador de Google (google/) y la recuperación de contraseña por correo (recuperacion/).

Criterio 9 de la rúbrica

CORS: ¿quién puede llamar a la API?

Definido en security/cors/CorsConfig.java, un único bean CorsConfigurationSource registrado para /** — no se usa @CrossOrigin disperso en los controllers.

Orígenes permitidos

  • Dominios de desarrollo local: localhost, 127.0.0.1 (varios puertos de Live Server), localhost:5173 (Vite)
  • https://*.herokuapp.com
  • https://petcore-seven.vercel.app y https://petcore-oerh.vercel.app (frontend en Vercel)
  • https://localhost y capacitor://localhost (apps nativas Android/iOS)
  • Orígenes extra vía variable de entorno security.cors.extra-origins, sin tener que recompilar

Configuración

  • allowCredentials = true → obligatorio porque la sesión viaja en una cookie, no en un header
  • Métodos: GET, POST, PUT, PATCH, DELETE, OPTIONS
  • Headers permitidos: Origin, Content-Type, Accept, Authorization, X-Requested-With, Cookie...
  • Headers expuestos: Set-Cookie, Cookie, Authorization, Content-Disposition
  • maxAge: 3600s (el navegador cachea el resultado del preflight)
Detalle fino para impresionar al jurado: WebSocketConfig.java tiene que repetir manualmente esta misma lista de orígenes para el handshake de /ws, porque Spring Security no comparte automáticamente la configuración de CORS HTTP con WebSocket. El propio código lo advierte en un comentario.

Criterios 7 y 8 de la rúbrica

Spring Security: autenticación, roles y "deny by default"

security/config/SecurityConfig.java — el archivo más importante de toda la API para la defensa (1219 líneas).

Configuración base de la cadena de filtros

  • CSRF deshabilitado — justificado porque la API es stateless con JWT y no usa formularios HTML tradicionales
  • sessionCreationPolicy(STATELESS) — Spring Security no guarda sesión en servidor
  • RestAuthHandlers como authenticationEntryPoint y accessDeniedHandler → respuestas 401/403 en JSON consistente, no la página de error por defecto
  • JwtCookieAuthFilter insertado antes de UsernamePasswordAuthenticationFilter

Roles del sistema (Authorities)

  • ROLE_Administrador
  • ROLE_Veterinario
  • ROLE_Recepcionista
  • ROLE_Farmaceutico
  • ROLE_Propietario (usuario de la app móvil, dueño de mascotas)

Constante STAFF = {ADMIN, VET, FARM, RECEP} y helper staffMas(extra...) para endpoints que comparte el personal con el propietario.

El patrón clave: "deny by default"

Cada tabla tiene su propio método reglasX(auth) dentro de SecurityConfig con una regla explícita por endpoint (hasAuthority, hasAnyAuthority). Al final de toda la cadena hay una única línea que cierra el sistema:

auth.anyRequest().denyAll();

Esto significa que cualquier ruta nueva que se agregue sin una regla explícita queda bloqueada automáticamente — nadie puede "olvidarse" de proteger un endpoint nuevo. Es el punto de seguridad más fuerte para mencionar en la defensa.

Ejemplos reales de reglas por endpoint

Punto honesto para la defensa si preguntan por debilidades: el handshake de /ws/** está marcado como permitAll() a propósito — el canal WebSocket aún no valida el JWT en la conexión inicial. Es una mejora pendiente, decirlo con seguridad demuestra dominio real (criterio 10).

Autenticación

JWT firmado + cookie httpOnly: el corazón de la seguridad

PetCore combina lo mejor de dos mundos: un token JWT (sin estado, sin tabla de sesiones en BD) pero entregado dentro de una cookie httpOnly en vez de guardarlo en localStorage. Ver la comparación completa en Conceptos clave.

security/jwt/JWTUtils.java

  • Firma con HMAC-SHA256 (Keys.hmacShaKeyFor + SignatureAlgorithm.HS256)
  • Secreto inyectado por variable de entorno SECRET_KEY_JWT (nunca hardcodeado)
  • Claims del token: id, rol, tipo ("EMPLEADO" o "PROPIETARIO"), sub = correo, iss, exp
  • Expiración configurable vía JWT_EXPIRATION (ej. 24h)

security/jwt/JwtCookieAuthFilter.java

  • Filtro OncePerRequestFilter que corre en cada request
  • Lee la cookie authToken (empleados) o authTokenPropietario (dueños) — prioriza empleado si llegan ambas
  • Construye el Authentication de Spring con autoridad "ROLE_" + rol
  • Sesión deslizante: si el token es válido, renueva la cookie en cada petición (TTL por defecto 900s = 15 min)

Dos audiencias, dos cookies

El sistema distingue entre empleados (Administrador/Veterinario/Recepcionista/Farmacéutico, usan el portal web) y propietarios (dueños de mascotas, usan la app móvil). Cada tipo tiene su propio login, su propio endpoint /api/auth/me/... y su propia cookie, firmadas con la misma utilidad JWTUtils pero mantenidas separadas para no mezclar permisos.

Modelo de datos

Entidades JPA y relaciones principales

EmpleadosEntity TBL_EMPLEADOS

El "hub" del sistema junto a Mascotas. @ManyToOne a RolesEntity (obligatorio) y a TurnosEntity (opcional). Tiene ~17 relaciones @OneToMany inversas: Expedientes, Citas, Ventas, Hospitalización, Prescripciones, Compras, Notificaciones, etc. — casi todo registro queda enlazado al empleado que lo creó o gestionó.

RolesEntity TBL_ROLES

Catálogo simple: rol_id, rol_nombre. Los 5 roles (Administrador, Veterinario, Farmacéutico, Recepcionista, Propietario) se combinan con el prefijo ROLE_ para formar las authorities de Spring Security.

PropietariosEntity TBL_PROPIETARIOS

Usuarios del portal móvil / dueños de mascotas. Incluye pro_google_id para vincular el login con Google. @OneToMany a Mascotas, Ventas y Notificaciones.

MascotasEntity TBL_MASCOTAS

@ManyToOne obligatorio a Raza, Pelaje y Propietario. @OneToMany a Citas, Cartillas, Expediente, Hospitalización, Tareas Médicas, Antiparasitarios y Alergias.

Convención técnica a mencionar: todas las relaciones directas usan fetch = LAZY (no cargan datos relacionados hasta que se piden explícitamente), las claves primarias usan GenerationType.IDENTITY (compatible con Oracle), y hibernate.default_batch_fetch_size=50 está configurado en application.properties para evitar el problema N+1 cuando se cargan colecciones completas.

Criterio 6 de la rúbrica

Validaciones e integridad de datos

Bean Validation en los DTO

Ejemplo real de EmpleadosDTO:

@NotBlank
@Email
private String empCorreo;

@Pattern(regexp = "^[0-9]{8}-[0-9]$")
private String empDui;

@Past
private LocalDate empFechaNac;

@JsonProperty(access = JsonProperty.Access.WRITE_ONLY)
private String empContrasenia;

El campo de contraseña nunca se devuelve en las respuestas JSON gracias a WRITE_ONLY — buen detalle de seguridad para mencionar.

Manejo centralizado de errores

exceptions/global/GlobalExceptionHandler.java (@RestControllerAdvice) — ningún controller ni service tiene try/catch; todo error sube hasta aquí y se traduce a un código HTTP consistente:

  • MethodArgumentNotValidException → 400 con mapa campo→mensaje
  • NotFoundException (de cualquier módulo) → 404
  • DuplicateException / DataIntegrityViolationException → 409
  • BadCredentialException → 401
  • CuentaInactivaException → 403
  • Exception genérico (no previsto) → 500

Cada módulo define sus propias 5 excepciones (ej. CitasNotFoundException) heredando de las clases base globales — así el handler central las atrapa a todas sin tener que registrar un handler distinto por cada uno de los 51 módulos.

Tiempo real

WebSockets en el Backend

PetCore usa WebSocket puro/crudo, no STOMP — es decir, no usa @EnableWebSocketMessageBroker ni SimpMessagingTemplate (el "WebSocket de alto nivel" típico de los tutoriales). En su lugar implementa su propio protocolo mínimo.

config/websocket/WebSocketConfig.java

@EnableWebSocket + WebSocketConfigurer, registra un único endpoint: /ws, atado al handler personalizado.

config/websocket/EventoWebSocketHandler.java

Extiende TextWebSocketHandler. Mantiene un ConcurrentHashMap con todas las sesiones conectadas y expone difundir(evento, datos), que serializa {evento, datos} a JSON y lo envía a todas las sesiones (broadcast total — el frontend filtra qué eventos le interesan).

Detalles de producción (pensados para Heroku)

  • Ping cada 25s (@Scheduled) — el router de Heroku corta conexiones inactivas a los 55s, así que el ping evita que el WebSocket se desconecte solo.
  • Pool de hilos dedicado para los envíos — así un broadcast lento no bloquea el hilo HTTP que disparó el evento.
  • Para qué se usa: notificaciones en vivo (campanita de la sidebar), indicador de "conectado/desconectado" en el navbar, y actualización en caliente de la configuración institucional sin recargar la página.

Criterio 9 de la rúbrica

Configuración y despliegue en Heroku

application.properties

Todo externalizado a variables de entorno (cero credenciales hardcodeadas en el código):

  • BD: DB_URL, DB_USER, DB_PASSWORD, DB_DRIVER, DB_DIALECT
  • JWT: SECRET_KEY_JWT, SECURITY_JWT_ISSUER, JWT_EXPIRATION
  • Cookies: COOKIE_SECURE, COOKIE_SAMESITE, SESSION_TTL_SEGUNDOS
  • Cloudinary, VAPID (Web Push), Firebase, SMTP, Google OAuth
  • Pool HikariCP (máx. 8 conexiones) y Tomcat (máx. 30 hilos) ajustados al plan gratuito de Heroku

Procfile

web: java -Dserver.port=$PORT $JAVA_OPTS -jar target/API-0.0.1-SNAPSHOT.jar

Ejecuta el Jar generado por Maven usando el puerto que Heroku asigna dinámicamente ($PORT). system.properties fija java.runtime.version=17 para el buildpack.

Dominio real: petcore-8afada45fabc.herokuapp.com. Un workflow de GitHub Actions (keep-alive.yml) hace ping periódico para reducir el "cold start" del dyno gratuito.
