1 Documentación del sistema

Dos tipos: manual de usuario (con capturas de pantalla paso a paso, dirigido al personal de la clínica) y documentación técnica (cómo instalar y ejecutar el proyecto: backend con Maven, frontend estático, variables de entorno), más diagramas (casos de uso, entidad-relación) que explican el funcionamiento interno.

Indica la ubicación real de tu equipo (repositorio, carpeta de documentación, o anexo entregado al jurado). Prepárala con anticipación — es una pregunta de "sí o no" que no debería tomarlos por sorpresa.

Son audiencias distintas con necesidades distintas: el personal de la clínica (veterinarios, recepcionistas) necesita saber cómo usar el sistema sin jerga técnica, mientras que un desarrollador que dé mantenimiento necesita saber cómo está construido (arquitectura, variables de entorno, cómo correrlo localmente). Mezclarlas hace que ambos documentos terminen siendo inútiles para su audiencia real.

Típicamente: diagrama de casos de uso (qué puede hacer cada rol — es la base del criterio 8, protección de endpoints), diagrama entidad-relación (las 48 tablas y sus relaciones, ver Base de datos), y opcionalmente un diagrama de arquitectura (cómo se comunican frontend, backend, base de datos y app móvil). "Especie") para entender el patrón repetido en los 47 módulos antes de tocar cualquiera de los otros.

2-3 Diseño de interfaces (web y móvil)

Que la interfaz se adapta automáticamente al tamaño de pantalla donde se vea — un celular, una tablet o una computadora — reacomodando o escondiendo elementos para que siga siendo cómoda de usar, sin que el usuario tenga que hacer zoom o scroll horizontal.

Bootstrap 5.3.8, por su sistema de grid y utilidades ya probadas (botones, tarjetas, offcanvas) que aceleran el desarrollo sin tener que escribir CSS responsive desde cero para cada componente — complementado con CSS propio para la identidad visual de PetCore.

Combinando dos señales en JavaScript: el ancho de pantalla (window.innerWidth) y el navigator.userAgent para detectar si es un dispositivo móvil. Por debajo de cierto umbral (~992px) o en un dispositivo móvil detectado, la sidebar se colapsa en un menú hamburguesa flotante en vez de quedar fija a la izquierda.

El dashboard de Administrador prioriza indicadores generales (reportes, personal, inventario global), mientras que el del Farmacéutico está optimizado para velocidad operativa: el punto de venta (POS) es la pantalla principal, pensada para escanear/buscar productos rápido durante una venta, no para analizar datos.

Con disciplina de convenciones en vez de componentes reutilizables automáticos: una hoja de variables CSS compartida (style_global_compartido.css) que define colores, tipografía y tema oscuro/claro para todo el sitio; un patrón repetido de estructura HTML por tipo de página (dashboard, listado CRUD, formulario); y un controller común (estructura_base_controller.js) que genera la sidebar, navbar y lógica compartida en tiempo de ejecución para que no haya que copiar-pegar ese HTML en cada una de las 60+ páginas.

4-5 Funcionalidad del sistema (CRUD web y móvil)

Crear, Read/Leer, Update/Actualizar, Delete/Eliminar — las cuatro operaciones básicas que se pueden hacer sobre cualquier dato persistente del sistema, por ejemplo un empleado, una mascota o un producto.

Elige un módulo simple (ej. Especie/Raza/Pelaje): Crear un registro → Leer el listado actualizado al instante → Actualizar ese registro y ver el cambio reflejado → Eliminar y confirmar que desaparece. Narra en voz alta que cada acción dispara un fetch al endpoint correspondiente.

El interceptor global de fetch (fetch_con_credenciales.js) detecta errores 502/503/504 y reintenta automáticamente con backoff creciente (1.5s, 3s, 5s, 8s) — pensado para el "cold start" de Heroku. Si después de los reintentos sigue sin responder, se muestra una alerta clara al usuario en vez de dejar el formulario colgado sin explicación.

El backend expone endpoints de búsqueda paginada (apoyados en config/paginacion/PaginacionUtils.java) que devuelven solo un bloque de resultados por vez en vez de la tabla completa — importante para módulos con muchos registros como Expedientes o Ventas, donde cargar todo de golpe sería lento y gastaría memoria innecesaria.

Respuesta honesta recomendada: el sistema actualmente sigue la estrategia más simple ("el último que guarda, gana" — last write wins), sin bloqueo optimista por versión. Es una mejora identificada: agregar un campo de versión (@Version de JPA) a las entidades más sensibles a concurrencia (ej. inventario, citas) para detectar y avisar si alguien más modificó el registro mientras tanto.

Las llaves foráneas (FK_*) de Oracle lo impiden por defecto: no se puede eliminar un registro padre (Mascota) mientras existan registros hijos (Expediente, Citas, Hospitalización) que dependan de él — la base de datos lanza un error de integridad referencial, que el backend traduce a un 409 Conflict en vez de dejar expedientes "huérfanos" apuntando a una mascota que ya no existe. Por eso PetCore usa baja lógica (EMP_ESTADO = 'Inactivo') en vez de borrado físico para registros con historial clínico.

6 Validaciones e integridad de datos

Es la verificación de que un dato cumple el formato o tipo esperado antes de guardarlo — por ejemplo, que un correo tenga el formato algo@dominio.com, que una fecha de nacimiento no sea futura, o que un campo numérico no contenga letras.

El DUI del empleado: debe cumplir el formato salvadoreño 00000000-0, validado con una expresión regular tanto en el DTO del backend (@Pattern) como con un CHECK CONSTRAINT en la propia base de datos Oracle.

El frontend valida para dar feedback inmediato sin esperar un viaje al servidor, pero se puede saltar fácilmente (herramientas de desarrollador, Postman). La validación que realmente garantiza la integridad de los datos ocurre en el backend — nunca se debe confiar en que un dato ya viene validado solo porque pasó por el frontend.

El input del frontend restringe la selección con accept="image/*", pero eso es solo una sugerencia del navegador. La validación real ocurre al subir el archivo: Cloudinary y/o el backend verifican el tipo MIME real del archivo antes de aceptarlo, y hay un límite de tamaño configurado (10MB) para evitar subidas abusivas.

A través de la tabla TBL_POSOLOGIA_FARMACO: cada producto farmacéutico tiene asociada su posología de referencia (dosis mínima/máxima recomendada), y el formulario de prescripción puede validar contra ese catálogo en vez de tener un valor fijo en el código — así agregar un medicamento nuevo con su propio rango de dosis no requiere tocar la lógica de validación, solo un nuevo registro en el catálogo.

7 Autenticación y roles de usuario

Cinco en total: Administrador, Veterinario, Recepcionista y Farmacéutico (personal, usan el portal web), más Propietario (dueño de mascotas, usa la app móvil).

El backend responde con un error de credenciales inválidas (401), sin especificar si fue el correo o la contraseña lo que falló — por seguridad, nunca se revela cuál de los dos campos fue el incorrecto, para no facilitarle información a alguien intentando adivinar cuentas válidas.

Un hash es el resultado de una función matemática de un solo sentido: a partir de la contraseña se puede calcular el hash, pero no al revés. Si guardaran la contraseña en texto plano y alguien accediera a la base de datos, tendría acceso directo a todas las cuentas; guardando solo el hash (con Argon2), aunque roben la base de datos no pueden recuperar la contraseña original.

Argon2 es el algoritmo ganador de la Password Hashing Competition (2015), diseñado específicamente para ser lento y costoso en memoria a propósito — eso dificulta mucho que un atacante pruebe millones de contraseñas por segundo (ataque de fuerza bruta) aunque tenga acceso a los hashes robados. Es considerado más resistente que alternativas más antiguas como MD5 o SHA-256 sin "salt", que fueron diseñadas para ser rápidas (lo contrario de lo que se necesita para contraseñas).

Respuesta honesta: el usuario no recibiría el código de recuperación y el flujo quedaría bloqueado en ese paso — es una dependencia externa del sistema. Una mejora posible sería agregar un mecanismo de reintento con cola, o un canal alterno (ej. recuperación asistida por un Administrador desde el panel de personal) para no depender 100% de que el correo llegue.

8 Protección de endpoints y vistas

El guard de estructura_base_controller.js detecta que no hay sesión válida y redirige automáticamente al login — nunca se llega a ver el contenido de la página protegida, ni por un instante.

401 Unauthorized significa "no sé quién eres" — no hay credenciales válidas (sin sesión, token expirado). 403 Forbidden significa "sé quién eres, pero no tienes permiso" — hay una sesión válida, pero el rol del usuario no está autorizado para ese endpoint específico. PetCore usa ambos correctamente: el filtro JWT determina 401, y las reglas de SecurityConfig.java determinan 403.

El bfcache (back-forward cache) es una optimización del navegador que restaura una página desde memoria al navegar "Atrás", sin recargarla ni re-ejecutar su JavaScript desde cero. PetCore escucha el evento pageshow y, si event.persisted es verdadero, fuerza un location.reload(), lo que vuelve a ejecutar la verificación de sesión y expulsa al usuario si ya cerró sesión.

Respuesta honesta: httpOnly protege contra robo vía JavaScript (XSS), pero no contra un atacante que intercepte el tráfico de red directamente (ataque "man-in-the-middle"). Contra eso protege HTTPS/TLS (toda la comunicación va cifrada en tránsito) y el atributo Secure de la cookie (solo se envía por HTTPS, nunca por HTTP sin cifrar) — ambos presentes en el despliegue de PetCore en Vercel y Heroku.

Es una debilidad real y reconocida: el handshake inicial de /ws no valida el JWT todavía. Sin embargo, el canal solo transmite eventos de notificación general (no datos sensibles por usuario específico), por lo que el impacto práctico es limitado — aun así, es la mejora de seguridad pendiente más clara a mencionar si preguntan por debilidades del sistema. Decirlo con seguridad, en vez de evitarlo, demuestra dominio real.

9 Despliegue

Frontend en Vercel, API/Backend en Heroku, base de datos en Oracle Cloud (gestionada con SQL Developer), y la app móvil instalada directamente en un dispositivo Android físico.

En el plan gratuito/económico de Heroku, el servidor "duerme" tras un período sin tráfico, y la primera petición después de eso tarda varios segundos extra en responder mientras el dyno despierta. PetCore lo maneja con reintentos automáticos en el frontend (backoff creciente ante 502/503/504) y un workflow de GitHub Actions que hace ping periódico para reducir cuánto tiempo pasa dormido.

El frontend (Vercel) hace peticiones HTTP/HTTPS al backend (Heroku) usando su URL pública, configuradas como origen permitido en CORS. El backend (Heroku) se conecta a la base de datos (Oracle Cloud) usando el driver JDBC ojdbc11 y credenciales en variables de entorno — son tres servicios totalmente independientes que solo se "conocen" por configuración, no por estar en la misma red o servidor físico.

Precisamente el diseño stateless de la autenticación: la sesión no vive en memoria del servidor (no hay una tabla ni un mapa de sesiones activas), sino en el JWT dentro de la cookie del navegador del usuario. Si el dyno se reinicia, el nuevo proceso puede validar esa cookie igual que el anterior, porque la firma del JWT depende solo del secreto compartido (SECRET_KEY_JWT), no de ningún estado que se haya perdido.

10 Dominio teórico y funcional

~47 módulos funcionales en el backend (uno por entidad principal) y 48 tablas en la base de datos Oracle, organizadas en 6 dominios: personal, catálogos clínicos, atención clínica, inventario/ventas, comunicación y RRHH.

Respuesta sugerida (ajústala con tu equipo): coordinar el modelo de permisos "deny by default" a través de ~47 módulos sin dejar ningún endpoint sin proteger, y sincronizar manualmente la lista de orígenes de CORS entre la configuración HTTP normal y el handshake de WebSocket.

Ajusta esta respuesta a la realidad de tu equipo (por módulos, por capa frontend/backend/BD, por rol de usuario del sistema). Lo importante para el jurado es ver que hubo una división clara y que cada integrante puede explicar tanto su parte como, al menos a grandes rasgos, el resto del sistema — el criterio 10 evalúa a cada integrante individualmente.

Buena respuesta honesta, ya identificada en el propio código: securizar el handshake de /ws (hoy público, pendiente validar el JWT ahí también), añadir bloqueo optimista por versión para evitar condiciones de carrera en ediciones simultáneas, y agregar cacheo de assets estáticos en el Service Worker para mejor soporte offline.

Es el requisito de la institución para esta defensa (gestionado con SQL Developer en Oracle Cloud). Técnicamente, el proyecto usa el driver ojdbc11 + Hibernate configurado con el dialecto de Oracle, y GenerationType.IDENTITY en las entidades está elegido específicamente por ser compatible con el motor de autoincremento de Oracle.

Buena respuesta de arquitectura: agregar multi-tenancy (una columna o esquema separado por clínica para aislar los datos de cada una), mover de un único dyno de Heroku a múltiples instancias con balanceo de carga, y posiblemente separar la base de datos por clínica o agregar particionamiento en las tablas más grandes (Expedientes, Citas) para que el rendimiento no se degrade con el volumen.

En una arquitectura por capas clásica (todos los controllers juntos, todos los services juntos), con 47 entidades esas carpetas se vuelven inmanejables — encontrar todo lo relacionado a "Citas" implica saltar entre 5 carpetas distintas. La organización modular por feature agrupa todo lo de una entidad (controller, service, repository, entity, dto, exceptions) en una sola carpeta, lo que facilita trabajar en equipo sin pisarse (cada integrante puede "dueño" de sus módulos) y entender un dominio completo sin saltar por todo el proyecto.
